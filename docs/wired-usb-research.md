# Wired USB research (2026-09-23)

Baseline before edits: clean `main` working tree; 15 `unittest` cases passed. Existing Bluetooth RFCOMM, iAP2 link/parser/probe and local PPM/H.264 demo were inspected. No Wi-Fi handoff connection or CarPlay-over-IP sender existed. The new work keeps the Bluetooth path and stops at the same unverified authentication boundary.

## Role and evidence

Our required direction is **Pi 4B as phone/source USB device → Subaru as USB host/head unit**. [carplayd](https://github.com/lvalen91/carplayd) proves a different arrangement: an iPhone switches to host and a Pi gadget acts as a CarPlay **accessory**. Its FunctionFS/iAP2/NCM construction is useful for Linux mechanics, but its identification and authentication roles cannot be copied into a fake phone. [CPC200-CCPA_resources](https://github.com/lvalen91/CPC200-CCPA_resources/blob/main/documentation/01_Firmware_Architecture/hardware_platform.md) likewise describes an adapter that can present an **accessory** gadget to an iPhone. Its `g_iphone.ko` name is not evidence of an iPhone emulator. The `1314:1520`/`1314:1521` box-to-companion interface is unrelated to the vehicle's phone-facing port and is not used here.

`carplayd`'s documented `0x51` role-flip work belongs to that accessory/iPhone-host topology. The `0x52` observation below is a **host-to-real-iPhone** request from a separate phone capture. They must not be treated as interchangeable commands.

## Gadget mechanism decision

[ConfigFS](https://docs.kernel.org/usb/gadget_configfs.html) builds static device/configuration/function descriptors and binds the UDC after links are complete. Its `ncm` function is the smallest reversible W1 network gadget. [FunctionFS](https://docs.kernel.org/usb/functionfs.html) can provide vendor interface descriptors, endpoint streams, interface-scoped setup events and altsetting events, while ConfigFS supplies NCM. It does **not** give a userspace FunctionFS process control over every device-level EP0 request or dynamic `bNumConfigurations`; standard composite code handles many requests itself. Therefore ConfigFS + FunctionFS is a candidate for mux data only after its descriptors and direction are known. It is not yet demonstrated sufficient for the observed `0xC0/0x52` configuration reveal.

[GadgetFS](https://github.com/torvalds/linux/blob/master/include/uapi/linux/usb/gadgetfs.h) exposes device EP0 setup events and endpoints but handles or checks some descriptors. [Raw Gadget](https://docs.kernel.org/usb/raw-gadget.html) exposes nearly all requests and arbitrary descriptor responses, but upstream labels it a debugging facility rather than production mechanism. A small composite gadget function/kernel change could intercept exactly the Apple device request while retaining the kernel NCM function. **TODO:** after a Subaru capture, test whether a userspace GadgetFS path or a narrow composite extension can deliver the observed behavior; choose a kernel module only with a concrete unsupported EP0/configuration requirement. Do not graft the accessory-facing `carplayd` gadget onto the phone role.

The current `carpi usb setup` is deliberately a **development NCM enumeration gadget**, VID/PID `1d6b:0104` and product `carpi NCM test gadget`. These are Linux example IDs for lab work, not a registered product identity. There is no Apple research/spoof mode. The Pi-side ConfigFS view reports planned values; only host `lsusb -v` confirms actual descriptors, endpoints and alternate settings.

## Questions for a sanitized Subaru capture

1. Does the host issue Apple `0xC0/0x52`, another vendor request, or no Apple-specific request with the development identity? What reset/disconnect follows?
2. What device/configuration descriptors does it request, in what order, and which `SET_CONFIGURATION`/`SET_INTERFACE` values appear?
3. Does it look for mux/lockdown before iAP2, and which side opens each channel?
4. Which NCM pair and MAC string does it use; when does carrier appear and what IPv6 link-local address does each peer choose?
5. Which iAP2 messages and authentication roles precede CarPlay-over-IP? Never publish raw credentials, keys, certificates or full captures by default.
